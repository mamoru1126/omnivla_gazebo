OMNIVLA × GAZEBO HARMONIC × ROS 2 HUMBLE

OmniVLA を Gazebo で自律移動させるまでの統合ガイド

ゴールまでの経路を 1m ごとに撮影したサブゴール画像を用意し、OmniVLA が「今見えている画像」と「今のサブゴール画像」から進路を出す ― サブゴールに着いたら次の画像へ切り替え、最終ゴールまでたどり着くまでを、リポジトリ mamoru1126/omnivla_gazebo を使って順に組み上げる手順です。 公式の重みは実写で学習されているので、まず Gazebo で集めたデータでファインチューニングしてから走らせます。

全体像

Docker コンテナを役割ごとに 3 つ並べ、ROS 2 のトピックでつなぎます。Gazebo が「ロボットの目と足」、 OmniVLA navigator が「どちらに進むかを決める頭」です。ファインチューニング時は Gazebo 側でデータを集め、学習コンテナで LoRA を学習します。

全コンテナは同じイメージ (docker-compose の sim / nav / explore / train / shell サービス)。ホストネットワーク共有で ROS 2 と gz-transport がつながる。

1 ステップ (約 0.33 秒) で何が起きるか

OmniVLA は「遠くのゴールまでの完全な経路」は出しません。出すのはこの先約 2.7 秒分の 8 点の軌跡だけです。 それを少しだけ実行して、また撮り直して推論する、を繰り返すことで前に進みます。

② サブゴールに「着いた」の判定
距離 0.3m 以内 かつ ロボットの向きとその画像を撮った向きの差が 25° 以内。 曲がり角で向きがずれたまま次へ進む (角を内側に詰める) のを防ぎます。少しずれて後ろに回った場合は通過扱いにして先へ進みます。
④ 制御
8 点の k 点目は (k+1)/3 秒後の位置と向きです。手前 5 点の「進んだ道のり」と「向きの変化」に合う一定の速度・角速度を求めて、 モデルが予測した曲がり方・減速をそのまま実行します。

ロードマップ

段階手順ゴール目安時間
A. 準備1〜2イメージ構築・重み取得1〜1.5 時間 (大半はダウンロード)
B. 適応3〜4Gazebo でデータを集めて LoRA 学習収集 2〜3 時間 + 学習 数時間
C. 走行5〜6サブゴール画像をたどってゴールまで自律移動30 分
D. 評価7ランダムな経路で成功率を測る30 分〜
前提: Linux + NVIDIA GPU (VRAM 24GB, RTX 3090 クラス) + Docker + NVIDIA Container Toolkit。 コマンドはすべてリポジトリのルートで実行します。Gazebo と学習は同じ GPU に同時に載らないので、学習の前に docker compose stop sim します。

A. 環境構築

  1. Docker イメージを作る

    20〜40 分1 回だけ
    git clone https://github.com/mamoru1126/omnivla_gazebo
cd omnivla_gazebo
cp .env.example .env
docker compose build

    Ubuntu 22.04 / Python 3.10 / ROS 2 Humble / Gazebo Harmonic / PyTorch 2.2 / OmniVLA (コミット固定) を 1 つのイメージにまとめます。

  2. 公式チェックポイントを取得する

    回線次第 (約 16GB)
    docker compose run --rm shell bash scripts/download_checkpoints.sh
# 任意: GPU で推論できるか確認 (Gazebo なし) → ./runs/smoke_test/*.jpg
docker compose run --rm shell python3 scripts/smoke_test_policy.py

B. Gazebo の見え方に適応させる (データ収集と学習)

  1. お手本走行を自動で集める

    1 エピソード約 1 分GUI なしが速い
    HEADLESS=true WORLD=office_0 docker compose up sim                # 端末 1
WORLD=office_0 EPISODES=150 docker compose run --rm explore        # 端末 2 → /data/raw/office_0/

    各エピソードで「ランダムな位置にテレポート → ランダムなゴールまで経路計画 → 0.3 m/s で追従しながら画像と真値位置を 3Hz で記録」を繰り返します。

    外乱つき収集 (既定で有効)
    走行中、数秒おきにわざとロボットを経路から外し (最大 0.7m 程度)、そこからお手本が経路へ戻る様子を記録します。 外乱で動いた区間は正解に使わず、「外れた状態から戻る」動きだけを学習させます。 これが無いとモデルは経路の上を走る状態しか知らず、曲がり角で少しずれただけで予測が崩れて衝突します。

    見た目の多様性が汎化に効くので、ワールドを増やして集めるのもおすすめです:

    docker compose run --rm shell python3 tools/generate_worlds.py --worlds office park --seeds 1 2 3
# → office_1..3, park_1..3。WORLD=office_1 などで sim と explore を起動
    確認: docker compose run --rm shell python3 training/inspect_dataset.py /data/raw --num_viz 16 で 1 フレームあたりの移動量 ≈ 0.1m、perturbed_frames > 0、正解軌跡 (緑) が画像上の進行方向と一致していること。

  2. LoRA で学習する

    5000 step で数時間sim は停止
    docker compose stop sim
docker compose run --rm train      # → runs/<run>/checkpoints/step_005000/
    • 公式と同じ設定: 全 Linear 層に LoRA (r=32)、軌跡ヘッドも学習、lr 1e-4
    • 自動走行のデータはほとんど直進なので、曲がる場面と経路から戻る場面を多めに引いて学習します
    • 500 step ごとに検証誤差 (ADE) が出ます。turn は曲がる場面、recovery は戻る場面の誤差
    VRAM が足りないとき: batch_size: 1 にして grad_accumulation_steps を増やす、 または lora_target: llm。中断した学習は --resume_from runs/<run>/checkpoints/step_XXXXXX --max_steps <追加 step> で再開できます。

C. Gazebo で自律移動

  1. 目的地までのサブゴール画像列を作る

    1〜2 分
    docker compose up sim                                             # 端末 1 (GUI あり)
docker compose run --rm shell ros2 launch omnivla_gazebo topomap.launch.py \
    world:=office_0 out_dir:=/data/goals/demo goal_x:=7.5 goal_y:=4.0  # 端末 2

    地図上で現在位置から (7.5, 4.0) までの経路を計画し、1m ごとにロボットをテレポートさせて前方の画像を撮影します。 撮り終えたらロボットはスタート位置に戻ります。

    なぜ 1 枚でなく列にするのか
    OmniVLA は数 m 先までしか見通せない反応型の方策です。部屋をまたぐ遠いゴールは、見える範囲の画像を順にたどる方が安定します。
    座標の選び方
    ros2_ws/src/omnivla_gazebo/maps/office_0.png が地図 (黒=障害物, 赤=スポーン位置)。 引数は 7.5 のように小数で書く。作り直すときは overwrite:=true。

  2. 学習したモデルで走らせる

    モデル読み込み 1 分 + 走行 1 分
    # スタート姿勢に戻す (走行後や sim 再起動後は必須)
docker compose run --rm shell ros2 run omnivla_gazebo teleport --world office_0 --goal_dir /data/goals/demo
# 走行 (起動するとすぐ走り出す)
FINETUNED_DIR=/runs/<run>/checkpoints/step_005000 GOAL_PATH=/data/goals/demo docker compose run --rm nav

# 様子を見る (端末 3)
docker compose run --rm shell ros2 run rqt_image_view rqt_image_view /omnivla/debug_image

    デバッグ画像には「現在画像 + 予測軌跡」「今のサブゴール画像」「俯瞰の軌跡」が並びます。 ログに subgoal -> 3/14 のように進捗が出て、最後に final goal reached で停止します。

    実績: office_0 で廊下を直進 → ドアを抜けて左に曲がり → 部屋の奥のゴールまで (約 14m, サブゴール 15 枚) 到達。

D. 成功率の評価

  1. ランダムな経路で成功率を測る

    20 タスクで 30 分程度
    docker compose up sim                                                          # 端末 1
FINETUNED_DIR=/runs/<run>/checkpoints/step_005000 docker compose run --rm nav  # 端末 2 (空ならゼロショット)
docker compose run --rm shell ros2 launch omnivla_gazebo eval.launch.py \
    world:=office_0 num_tasks:=20 mode:=route min_dist:=4.0 max_dist:=12.0 label:=finetuned   # 端末 3

    評価ノードが「ゴールまでのサブゴール画像を撮る → スタートへテレポート → 走行 → 到達/タイムアウト/衝突を判定」を自動で繰り返し、 runs/eval/<label>_<world>_<時刻>/summary.json に成功率・SPL・衝突回数をまとめます。 seed が同じならタスクも同じなので、ゼロショットと学習後をそのまま比較できます (mode:=single は 2〜5m 先のゴール画像 1 枚)。

走行ログと解析

navigator は走行ごとに log/nav/<日時>/ へログを自動で保存します (git 管理外)。

ファイル中身
steps.csv推論ごとの位置姿勢, サブゴール, 予測 8 点, 指令 (v, ω)
events.log / summary.jsonサブゴールの切り替え, 到達したか, 終了理由
debug/, raw/, goals/毎ステップのデバッグ画像, カメラ画像, ゴール画像
 
python3 tools/plot_nav_log.py log/nav/latest
# → overview.png (地図上の軌跡と予測), timeline.png, report.txt

report.txt は失敗の原因を切り分けます: 予測がサブゴールと逆を向いた = モデル側、 予測した旋回を実行できていない = 制御側。ログの共有は別リポジトリ (omnivla_gazebo_logs, private) に push します。

実機へ持っていくとき

Gazebo での部品実機での置き換え
/camera/image_raw実カメラのトピック (image_topic)。画角・高さを学習時と近づける
/odom (真値)自己位置推定の出力。無い場合は到達判定を画像の類似度 (reach_check: image) にする
テレポートで作るサブゴール画像列手動走行しながら topomap.launch.py mode:=distance で記録
学習データ (自動走行)実機の走行ログ (画像 + オドメトリ) を同じ形式に変換して追加学習

推論部分 (omnivla_nav/policy.py) は ROS に依存しないので、ROS 以外のロボット制御系からもそのまま呼べます。

つまずきやすい点

症状原因と対処
Gazebo の画面が出ないホストで xhost +local:root。不要なら HEADLESS=true
waiting for camera image が続く描画に GPU が必要。NVIDIA Container Toolkit を確認。docker compose logs sim
テレポートできない / トピックが見えないコンテナ間で GZ_PARTITION, ROS_DOMAIN_ID を揃える (.env)
CUDA out of memory学習時は docker compose stop sim
ゴールと逆を向いて走り出すスタート姿勢に戻していない。走行前に teleport を実行
曲がり角で外に膨らむ・ぶつかる外乱つきで集めたデータが足りない。explore で追加収集して学習し直す

用語

VLA
Vision-Language-Action。画像と指示からロボットの行動を直接出力する大規模モデル
OmniVLA
画像・位置・言語のどれでもゴールを指定できるナビゲーション用 VLA (7B, OpenVLA ベース)
サブゴール / topomap
経路沿いに 1m ごとに撮った画像の列。これを順にたどって遠いゴールへ行く
waypoint
モデルが出力する 8 点の目標位置と向き (ロボット座標: x 前, y 左)。k 点目は (k+1)/3 秒後
ゼロショット
Gazebo のデータで追加学習していない、公式の重みそのままの状態
LoRA
元の重みは固定し、小さな追加行列だけを学習する手法。保存も数百 MB で済む
外乱つき収集 (DART)
お手本走行をわざと乱して経路から外し、戻る動きを学習データに加える手法
SPL
成功率を経路の効率で重み付けした指標 (最短経路長 / 実際の走行距離)
